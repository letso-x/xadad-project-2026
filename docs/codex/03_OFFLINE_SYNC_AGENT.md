# Offline sync agent

## Outcome

Build durable local-first mobile data and synchronisation foundations. Work must survive network loss, process death, device restart and database upgrades. Coordinate any required API idempotency/concurrency extensions with backend ownership and document the shared contract.

## Inspection

Discover MAUI project paths, supported platforms/workloads, local entities, SQLite package and migrations, repositories, API client, authentication services, DI and file storage. Investigate historical “Cannot add a PRIMARY KEY column” by inspecting actual migrations; do not assume old defects persist. No destructive database reset as an upgrade strategy.

## Required design and implementation

1. Maintain LocalId Guid and nullable ServerId long for offline-capable server entities. Preserve server IDs on download; maintain mappings and dependencies for new form/section/field/response/evidence operations. Server-generated snapshot IDs must be reconciled against stable snapshot keys without guessing identity sequences. Offline form creation needs a cached eligible version and deterministic reconciliation contract; do not regenerate from a newer live template at sync time without surfacing a conflict.
2. Store only needed client/project summaries, form snapshots/project fields/sections/fields/responses, evidence metadata, template/library metadata, operations and conflicts. Use versioned local migrations with rollback/recovery tests; preserve queued payloads and file references during upgrade.
3. Write local edits and outbox operations in one SQLite transaction. Update UI from durable local state. Each operation includes stable LocalOperationId, entity local/server IDs, operation type, payload, creation time, retry count, last attempt/error, status and dependencies. Payloads must not persist bearer tokens. Support Pending, Processing, Completed, Failed and Conflict; recover interrupted Processing safely after restart.
4. Copy captured files to app-owned durable storage before reporting save success. Persist metadata and upload intent; handle crashes between file copy and SQLite commit and document orphan cleanup. Keep files referenced by pending/failed/conflicting operations. Do not store large image blobs in SQLite. Upload only to API multipart POST; preserve qms-evidence server handling and compensation.
5. Cover UpdateQCFormProjectField, UpdateQCResponse, UploadEvidence and the full mobile create/submit/signoff workflow. Respect dependency order: create/reconcile IDs → field values/non-signature evidence → submit → Signature evidence (if not already uploaded while editable) → signoff. A locally captured image is pending evidence, not a valid server signoff. Recompute/validate current content after resubmit; do not replay an old signature silently as consent to corrected content.
6. Use practical server-backed idempotency for create/upload/signoff and other retry-sensitive transitions. Bind client operation key to authenticated principal/resource and request fingerprint; persist outcome atomically with database effects where possible. Same key/same request replays the result; same key/different request conflicts. Handle concurrent retries and storage/DB split failures. A local Completed flag alone does not protect the lost-response window.
7. Define optimistic concurrency with server revision/token and expected version. Reject stale edits/lifecycle changes; preserve local and server versions with actionable reason. Do not trust device clocks or silently use last-write-wins for quality records. Keep pull/cache refresh from replacing dirty local records. Do not assume UpdatedAt gives complete ordered change tracking; use a verified cursor/paging scheme appropriate to existing APIs.
8. Handle timeout/DNS/refused/reset/network loss, 401, 403, 409, 500 and unavailable API. Retry transient errors with bounded backoff; pause for authentication restoration; treat permission/business/validation failures as actionable rather than endless retry. NetworkAccess.Internet is only a hint. Serialize conflicting per-record operations; cancellation/restart must not mark unfinished work completed.
9. Keep sessions in SecureStorage, refresh through supported Supabase flow, verify linked active QMS identity online, and pause sync if auth cannot be restored. Scope local data/queue to owner/account; prevent another user's login from uploading prior work as their own. Preserve old unsynced data on logout and expired sessions with explicit locked recovery behavior. Offline access policy must be documented; offline mode cannot establish fresh server permissions.
10. Implement and verify encrypted SQLite/local storage on Android/iOS using supported packages/platform facilities. Key protection must use secure platform storage; include rotation/recovery behavior. Protect local evidence files as well as DB content according to platform capability. If unavailable, mark encryption incomplete and a release gate; plain SQLite plus SecureStorage is not encrypted SQLite.

## Verification and handoff

Run AT-13 through AT-17 and AT-25 applicable cases on actual available platform/device; include forced termination and lost server response. Test upgrade of a populated database with dirty operations and evidence files. Record encryption verification separately for Android/iOS. Handoff local repository/application service APIs, state notifications, sync triggers, conflict models and error messages to UI agent. Do not require Pages to orchestrate SQL/HTTP.
