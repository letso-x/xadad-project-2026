## Required work

1. Inspect QCForm 9's current state before testing; its reported Draft state is historical. Retain approved QCForm 8 and its historical signoff. Use fresh synthetic forms for correction/retry/concurrency tests.
2. Implement or repair the exact lifecycle: Draft/InProgress → Submitted → Approved or ReturnedForCorrection → edit → Submitted. ReturnedForCorrection edits include project fields/responses/ordinary evidence. Submitted permits controlled signature evidence/signoff only; Approved/Cancelled are read-only. Use conditional transactional state updates so competing requests cannot bypass guards.
3. Reuse FieldValueValidator for dynamic values. Snapshot project fields, sections and fields atomically from the selected active version. Preserve template version identity and every render/validation attribute. Repeated create/generation must not duplicate a snapshot. Enforce form/field membership and server-owned actors/timestamps in all writes.
4. Inspect QCFormContentHashService. Define deterministic canonical signable content and stable ordering/types/null handling. Keep SHA-256 lowercase hex (64 chars); exclude signature evidence and signoff collections. Avoid hashing volatile workflow metadata that changes solely due to sign/approve operations. If the existing contract includes such data, document a versioned compatible repair instead of rewriting old hashes. Current relevant header/details, project-field values, response values and non-signature evidence remain bound.
5. Preserve historical QCSignOff rows/hashes. On sign, compute current hash server-side; validate Submitted state, evidence type Signature, same form and uploader = current signing user, and configured signing authority. On approval compute current hash again and require the applicable current valid signoffs plus review/approval permission. A stale row is audit history, not current authorisation. Return-for-correction preserves rows; changed content invalidates their applicability. Do not relabel legacy hashes as new hashes.
6. Resolve submission/signature sequencing explicitly: server submit currently checks required project fields, non-photo/signature responses and required photos; signoffs are Submitted-only. Permit submission to enable signing, then require mandated valid signoffs before approval. Validate dual-signature requirements through explicit template/policy data, not invented roles. Do not require a Submitted-only signoff as a precondition to initial submit.
7. Inspect actual AuditEvent table/repositories. Add actor/action/entity/time for create, response/project-field edit, evidence, submit, correction, sign, approve; provide reusable foundation for core-module events. Couple database state changes and audit writes in the same transaction where possible; audit failure must not quietly report an unaudited critical transition as successful. Preserve storage-upload compensation if metadata insert fails; document cleanup failures without secrets.
8. Introduce configurable permission abstraction/policies and resource-access checks. QmsUser remains an active linked identity gate. Separate PerformInspection/SubmitInspection/ReviewInspection/ApproveInspection/ManageProjects/ManageTemplates and future module permissions; names are checkpoint examples, not proof they already exist. Do not invent final seven roles. Persist and configure explicit grants; test denial and inactive/unlinked users.
9. Provide/verify scoped, paginated list/resume APIs and stable DTOs needed by mobile. Publish actual field value JSON contracts, validation/error shapes, concurrency tokens and routes in the status handoff. Preserve existing exception mappings unless a concrete problem warrants change: ArgumentException 400, KeyNotFoundException 404, ConflictException/InvalidOperationException 409, unknown 500; unexpected errors must not expose details.
